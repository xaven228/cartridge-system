# Архитектура системы

## Общая схема

Система состоит из трёх основных частей:
- frontend на React
- backend на Spring Boot + Kotlin
- PostgreSQL для хранения данных

Запуск в штатном варианте идёт через `docker compose`.

## Компоненты

### Frontend

Frontend расположен в `frontend/`.

Технологии:
- React
- TypeScript
- Vite
- nginx в Docker-образе frontend

Frontend отвечает за:
- экран входа
- формы справочников и операций
- дашборд
- журнал
- отчёты
- пользовательский интерфейс модулей роста

### Backend

Backend расположен в `backend/`.

Технологии:
- Spring Boot 3
- Kotlin
- Spring Web
- Spring Data JPA
- Spring Security
- Flyway
- JWT

Backend отвечает за:
- REST API
- бизнес-правила
- права доступа
- аудит действий
- генерацию Excel/PDF отчётов
- фоновые проверки SLA и уведомлений

Основные пакеты:
- `controller`
- `service`
- `repository`
- `entity`
- `dto`
- `security`
- `exception`

### База данных

Используется PostgreSQL 16.

Изменения схемы применяются через Flyway-миграции из:

```text
backend/src/main/resources/db/migration
```

Это позволяет поднимать систему на новом сервере без ручного создания таблиц.

## Поток запроса

Типовой сценарий выглядит так:
1. пользователь открывает frontend
2. frontend отправляет запрос в backend
3. backend проверяет JWT и права
4. service-слой выполняет бизнес-логику
5. repository-слой работает с PostgreSQL
6. ответ возвращается во frontend

Для чувствительных действий backend дополнительно пишет запись в аудит.

## Безопасность

В проекте используются:
- вход по логину и паролю
- JWT-сессия
- авто-завершение при 30 минутах неактивности
- серверная проверка прав доступа
- аудит входов и изменений

Frontend скрывает недоступные разделы, но главным источником истины остаётся backend-проверка прав.

## Модули

Текущий активный модуль:
- `CARTRIDGE_ACCOUNTING`

Подготовленные направления роста:
- `HOTEL_INVENTORY`
- `HALL_REQUESTS`

Идея архитектуры в том, чтобы не ломать ядро учёта картриджей, а расширять систему отдельными bounded-context блоками.

## Масштабирование

Проект уже подготовлен к развитию:
- права доступа сделаны не только через роль, но и через детальные permission-флаги
- в интерфейсе и backend есть модульный реестр
- таблицы и API-слой подготовлены под дальнейшие сущности
- отчётность и аудит уже имеют расширяемую структуру

Это позволяет без полной переделки добавить:
- инвентаризацию оборудования
- заявки по залам
- дополнительные отчёты
- новые сценарии доступа
