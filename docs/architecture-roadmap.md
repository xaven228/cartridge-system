# Архитектура развития системы

## Что уже заложено

В текущем релизе добавлен модульный каркас, чтобы приложение развивалось без ломки ядра учёта картриджей:

- API реестра модулей: `GET /api/system-modules`
- Статусы модулей: `ACTIVE`, `PLANNED`
- Фронтенд отображает активный модуль и запланированные направления
- В БД добавлены подготовительные таблицы под следующий этап
- Backend поддерживает смешанный стек Java + Kotlin (новые модули можно писать на Kotlin)

## Модульный реестр

Текущий состав модулей:

1. `CARTRIDGE_ACCOUNTING` — активный модуль (учёт принтеров и картриджей)
2. `HOTEL_INVENTORY` — планируемый модуль (инвентаризация)
3. `HALL_REQUESTS` — планируемый модуль (заявки по залам)

## Подготовленные таблицы БД

Добавлена миграция `V15__prepare_future_hotel_modules.sql`:

- `rooms` — кабинеты/залы с привязкой к отделу
- `inventory_assets` — задел под инвентаризацию и движение активов
- `hall_requests` — задел под обработку заявок по залам

Эти таблицы не вмешиваются в текущую бизнес-логику и не меняют поведение действующих сценариев.

## Как развивать дальше

1. Включить бизнес-сервисы и контроллеры для `rooms`, `inventory_assets`, `hall_requests`
2. Добавить ролевые права на новые операции
3. Вынести отчёты по новым модулям в отдельные API
4. Перевести вкладки-заглушки на рабочие экраны

## Принцип совместимости

Текущий модуль учёта картриджей остаётся независимым от новых модулей. Новые функции добавляются как отдельные bounded context с собственными API и сценариями.

## Язык для следующих модулей

Новые блоки (`HOTEL_INVENTORY`, `HALL_REQUESTS`) реализуем на Kotlin в рамках текущего Spring Boot backend. Существующий Java-код не переписывается и продолжает работать как есть.
