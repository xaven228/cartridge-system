# Архитектура развития системы

## Что уже заложено

Система изначально строится так, чтобы текущий модуль учёта картриджей не пришлось ломать при расширении продукта.

Уже есть:
- API реестра модулей: `GET /api/system-modules`
- статусы модулей: `ACTIVE`, `PLANNED`
- подготовленные сущности и таблицы под рост системы
- детальные permission-флаги, а не только жёсткие роли
- единый аудит, который можно расширять новыми сущностями
- backend полностью на Kotlin

## Модульный реестр

Текущие направления:

1. `CARTRIDGE_ACCOUNTING` — активный рабочий модуль
2. `HOTEL_INVENTORY` — запланированное направление роста
3. `HALL_REQUESTS` — запланированное направление роста

## Что уже подготовлено в данных

В проекте уже есть база для следующих сущностей:
- `rooms` — кабинеты и залы с привязкой к отделу
- `inventory_assets` — задел под учёт активов и перемещений
- `hall_requests` — задел под сервисные заявки по залам

Это позволяет включать новые модули постепенно, не перестраивая существующее ядро.

## Как расширять дальше

Рекомендуемая последовательность:

1. активировать полноценные backend-сервисы и сценарии по `inventory_assets`
2. довести workflow `hall_requests` до полного боевого SLA-цикла
3. добавить новые permission-флаги под будущие действия
4. расширить отчёты и аудит под новые модули
5. при необходимости вынести крупные подсистемы в отдельные frontend-экраны и backend-сервисы

## Принцип совместимости

Основа проекта:
- модуль учёта картриджей остаётся самостоятельным
- новые функции подключаются отдельными bounded-context блоками
- backend проверяет права не по названию роли, а по конкретным разрешениям
- UI может расширяться вкладками без переписывания базовой авторизации и отчётности

## Технологическая линия

Текущий стек развития:
- backend: Kotlin + Spring Boot
- frontend: React + TypeScript
- БД: PostgreSQL
- миграции: Flyway
- развёртывание: Docker Compose

Это даёт нормальную основу для дальнейшего роста без смены платформы.
